자기소개

구조를 먼저 고민합니다

화면, 상태, 데이터 접근의 역할을 나누는 데 시간을 씁니다. 두 프로젝트 모두 MVVM을 바탕으로 서비스 계층을 분리했고, 프로토콜 추상화와 @MainActor·@ModelActor 격리로 각 계층의 책임과 스레드 안전성을 분명히 했습니다.

동작을 지키며 개선합니다

리팩토링은 UI/UX와 동작을 바꾸지 않고 내부 구조만 개선한다는 조건으로 진행합니다. Claude Code 멀티 에이전트 환경에서 항목별로 승인하고, 원자적 커밋 단위로 변경을 반영합니다.

Bloccode

아이소메트릭 2.5D 코드 블록 퍼즐 게임

플레이어가 코드 블록을 조립해서 캐릭터를 맵 위에서 움직이게 하는 퍼즐 게임입니다. 스테이지를 풀어 가며 순차 실행·반복문·조건문·함수 개념을 자연스럽게 익히도록 설계했고, 현재 App Store 출시를 준비하고 있습니다.

  • Swift
  • SwiftUI
  • SpriteKit
  • SwiftData
  • MVVM
  • XCTest

주요 기능

  • 이동·회전부터 반복·조건·함수, 보석 획득·스위치 작동까지 9종 코드 블록을 제공하고, 반복·조건 블록은 서로 중첩 가능
  • 10개 챕터, 69개 스테이지로 개념을 하나씩 도입하는 커리큘럼 구성
  • 보석·스위치와 문·포탈 기믹, 그리고 더 적은 블록으로 풀수록 높아지는 별점 시스템
  • 하나의 SwiftUI 코드베이스로 iPhone·iPad·Mac 화면 폭에 맞춘 레이아웃 제공, 라이트/다크 모드 대응

구현 포인트

  • View(SwiftUI) – ViewModel – Service/Model 계층에 SpriteKit GameScene을 분리해, 맵·캐릭터 렌더링과 게임 로직을 독립적으로 관리
  • 스테이지를 JSON으로 정의해 코드 수정 없이 콘텐츠를 추가할 수 있고, 기믹 필드는 옵셔널로 두어 기존 스테이지와 호환
  • 실행 중인 블록을 인덱스 경로([Int])로 추적해, 중첩된 블록 안에서 실패해도 정확히 어느 블록에서 막혔는지 표시
  • 별점은 컨테이너 블록을 제외하고 실제 동작 블록만 재귀적으로 세어 계산
  • GameViewModel을 @MainActor로 격리하고, 클리어 기록과 별점은 SwiftData로 저장
  • 블록 모델, 실행 엔진, 스테이지 데이터 무결성을 XCTest 단위 테스트로 검증

개발 방식

  • Claude Code로 멀티 에이전트를 구성해 개발과 리팩토링을 진행 (XcodeBuildMCP, Apple 공식 Xcode MCP, Context7)
  • 리팩토링은 UI/UX와 동작을 전혀 바꾸지 않고 내부 구조만 개선하는 조건으로 진행
  • 항목별 승인을 거쳐 원자적 커밋 단위로 반영

문제 해결 과정

  1. 챕터 해금 버그 → 메타데이터를 단일 원본으로 통합

    조건을 충족해도 챕터가 열리지 않았습니다. 챕터 메타데이터가 4~5곳에 하드코딩되어 값이 어긋난 것이 원인이어서, ChapterCatalog 한 곳에서만 정의하고 화면·뷰모델·서비스가 모두 여기서 조회하도록 바꿨습니다. 이후 챕터를 5개에서 10개로 늘릴 때 이 파일 하나만 수정했습니다.

  2. 중첩 블록 하이라이트 오류 → 인덱스에서 경로 기반으로 전환

    블록이 중첩되면 실행 중인 블록이 엉뚱한 행에 표시됐습니다. 정수 인덱스 하나로 위치를 추적해 자식과 최상위 블록의 인덱스가 충돌한 것이 원인이어서, 실행 위치를 경로 배열(currentBlockPath)로 바꾸고 재귀 실행 함수가 부모 경로를 넘겨받도록 했습니다.

  3. macOS에서만 드래그 불가 → RunLoop 모드 차이

    처음에는 제스처 충돌로 보고 우선순위를 올렸지만 해결되지 않았습니다. 다시 추적해 보니 macOS는 마우스를 누르는 동안 이벤트 트래킹 모드로 전환되어 롱프레스 타이머가 돌지 않았고, macOS에서만 타이머를 .common 모드로 등록해 해결했습니다.

  4. 69개 스테이지 정답 검증 → 시뮬레이터와 자동 테스트

    손으로 검증하다 풀 수 없는 스테이지가 섞여 들어갔습니다. 게임 실행 규칙을 옮긴 파이썬 시뮬레이터로 정답 도달 여부와 블록 수 기준을 통과한 스테이지만 생성하도록 했고, 유닛 테스트 54개와 UI 테스트로 회귀를 자동으로 잡습니다.

  5. 멀티플랫폼 레이아웃 깨짐 → 기기 종류가 아닌 화면 조건으로 분기

    iPad 온보딩에서 옆 페이지가 삐져나오고 iPhone 가로모드에서 콘텐츠가 잘렸습니다. iPad는 GeometryReader로 페이지 크기를 명시하고, iPhone 가로모드는 "사용 가능한 높이"를 기준으로 분기해 일러스트를 축소했습니다.

AI Money

개인 재무관리 iOS 앱

캘린더로 지출을 기록하고 차트로 분석하는 가계부 앱입니다. CreateML로 직접 학습시킨 텍스트 분류 모델을 사용해, 자연어로 입력한 질의를 분류하고 기간과 카테고리를 파악해 답변합니다.

  • Swift
  • SwiftUI
  • SwiftData
  • Combine
  • Charts
  • CoreML
  • CreateML
  • MVVM

주요 기능

  • 캘린더 기반 지출 추가·조회, 여러 지출을 카드 형태로 한 번에 입력
  • 기본 카테고리와 사용자 커스텀 카테고리 관리, 한국 공휴일 표시
  • Charts로 카테고리별 지출을 시각화하고, 연·월을 골라 기간별 통계 확인
  • 총 지출, 카테고리별 지출, 기간 비교, 평균 지출 등을 자연어로 물어볼 수 있는 챗봇

구현 포인트

  • CreateML로 학습한 ExpenseClassifier 모델로 질문 유형을 분류하고, 키워드·정규식 파싱으로 기간과 카테고리를 추출하는 하이브리드 방식
  • ConversationContext에 이전 대화의 기간·카테고리·질문 유형을 저장해 이어지는 질문을 처리
  • @ModelActor 기반 DataActor와 Sendable 구조체로 SwiftData를 비동기로 안전하게 조회
  • 서비스 인터페이스를 프로토콜로 추상화하고, ViewModel은 @MainActor로 격리
  • 캘린더의 선택 상태를 CalendarState enum으로 표현해 타입으로 관리

문제 해결 과정

  1. SwiftData 동시성 문제 → @ModelActor로 데이터 접근 격리

    챗봇이 화면용 ModelContext를 비동기 작업에서 그대로 사용해 스레드 안전성이 보장되지 않았습니다. @ModelActor 기반 DataActor로 조회를 격리하고, AI 서비스에는 ModelContainer를 넘기며 결과는 Sendable 구조체로 변환해 반환하도록 했습니다.

  2. 챗봇 질문 인식률 → CoreML 분류와 키워드 파싱의 하이브리드 구조

    소규모 학습 데이터로 만든 분류 모델만으로는 질문 유형을 안정적으로 맞히지 못했고, 기간·카테고리 값은 뽑아낼 수 없었습니다. 질문 유형은 CoreML 모델이, 기간·날짜·카테고리는 키워드와 정규식이 맡도록 역할을 나누고, 모델이 분류하지 못하거나 로드에 실패해도 키워드 파싱으로 동작하게 했습니다.

  3. 연속 질문 처리 → 대화 맥락 유지

    "이번 달 식비 얼마 썼어?" 다음에 "그럼 교통비는?"이라고 물으면 기간 정보가 없어 답하지 못했습니다. 기간·카테고리·질문 유형을 담는 ConversationContext를 두고, 새 질문에서 빠진 정보는 이전 맥락에서 채우도록 했습니다.

  4. 데이터 영속화와 정합성 → 메모리 배열에서 SwiftData로 전환

    앱을 종료하면 지출 내역이 사라졌고, 카테고리를 삭제해도 지출이 남아 차트와 내역이 어긋났습니다. 지출 모델을 SwiftData @Model로 전환해 추가·삭제·조회를 저장소 기준으로 통일하고, 카테고리 삭제 시 해당 지출도 함께 삭제하도록 연동했습니다.

  5. 중복 로직과 비대해진 뷰 → 포맷 통합과 MVVM 분리

    날짜·금액 포맷 코드가 화면마다 반복되고 뷰에 상태와 계산 로직이 몰려 있었습니다. 포맷 로직을 FormatHelper로 모으고, 상태와 계산은 Model과 ViewModel로 옮겼으며, 서비스는 프로토콜로 추상화했습니다.
